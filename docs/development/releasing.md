# Release Branch Strategy & Workflow

This document outlines our repository branching strategy, continuous integration workflow, and dependency management approach.

We have two types of releases:

 * mainline releases are from the `main` branch and include the latest development work.
 * stable releases come from a stable branch such as `release-1.7.x`.

 Both types of releases are released to PyPI, but are consumed differently.

  * For mainline releases, we build containers and release them to `quay.io`
    or users can install using `uv tool install` directly from PyPI.
  * For stable releases,
    our container builds are only available on `registry.redhat.io`.
    These builds require a RHEL subscription.
  * Additionally RPMs of stable releases are released as part of Red Hat Enterprise Linux.

The goal of our release strategy is to allow us to create all these types of artifacts with the minimal effort.

In addition, for container builds and RPMs, we often need to rebuild the containers and RPMs after
a release because the base image (for containers), installed RPMS (for containers),
or bundled Python dependencies (for containers *and* RPMs) have changed.
This is handled by the "post-release" branches detailed below.

## Branch Architecture

*   **`main` (Active Development):** Where all feature work and bug fixes land
*   **`post-release-main`:** A single long-lived branch that mirrors the latest release from main. It typically only receives automated lockfile updates and release-time syncs from `main`.
*   **`release-1.7.x`:** A stable minor release. Only includes bug fixes.
*   **`post-release-1.7.x`:** The equivalent of `post-release-main` for the releases from the stable branch.

The flat naming - `post-release-main` rather than the more natural `post-release/main` - is
to work around [a bug in the MintMaker branch of Renovate](https://github.com/redhat-exd-rebuilds/renovate/pull/83).

We'll promote two minor releases to stable branches a year,
one in spring and one in fall.
There may be intermediate minor version bumps that *do not* correspond to minor releases,
but are simply forced by semver rules.
A minor version bump must happen after a release branch is created to avoid version collisions:

```
1.5.0
  |  \
1.6.0 1.5.1 (release-1.5.x)
  |
1.6.1
  |
1.7.0
  |
1.7.1
  |  \
  |   1.7.2 (release-1.7.x)
1.8.0
```

In the above, 1.6.0 is never promoted to a stable branch,
and the bumps to 1.6.0 and 1.8.0 must occur even if there are only bugfixes landed on the main branch
at that point.

Stable branches are maintained for one year from release point, so there are a maximum of two
active at any one time.

Container tags in the repositories reflect this branch structure.
On `quay.io`, the only floating tag is `:latest`.
On `registry.redhat.io`, there are floating tags for each stable branch, such as `:1.7`.
The `:latest` tag on `registry.redhat.io` is a synonym for the most recent *stable branch*. (Not the most recently pushed container.)

## Component Interactions

*   **Renovate/MintMaker (Dependency Management):** Files dependency updates against all of the branches above, with a scope that differs per branch - see [What lands where](#what-lands-where).
*   **Konflux (CI/CD):** Builds containers, and publishes them to `quay.io` or `registry.redhat.io`.
*   **GitHub Actions (Orchestration):** Runs the test suites, publishes releases to PyPI and the MCP Registry, and keeps the `post-release-*` branches in sync with their base branches.

## What lands where

Each base branch is paired with a post-release branch that carries the released sources plus
packaging updates only. What that means in practice:

| Work | `main` | `post-release-main` | `release-1.7.x` | `post-release-1.7.x` | Notes |
| --- | :-: | :-: | :-: | :-: | --- |
| New features | ✓ | | | | |
| Bug fixes | ✓ | | ✓ | | On a stable branch these are backports; nothing lands there that is not on `main` first. |
| Routine `uv.lock` updates | ✓ | | | | Renovate lock file maintenance. A stable branch deliberately does not follow the latest dependencies. |
| Security updates to `uv.lock` | ✓ | ✓ | ✓ | ✓ | From a daily `uv audit` rather than Renovate, whose `pep621` manager only sees direct dependencies. |
| `Containerfile` base image | ✓ | ✓ | ✓ | ✓ | |
| Security updates to `rpms.lock.yaml` | ✓ | ✓ | ✓ | ✓ | |
| `.tekton` task updates | ✓ | ✓ | ✓ | ✓ | Konflux rejects tasks built from old containers, so these cannot be skipped. |
| `.konflux/requirements-*.txt` | ✓ | ✓ | ✓ | ✓ | Regenerated by a workflow whenever a PR changes `uv.lock`, not filed by Renovate. CVEs in these build-only dependencies are not chased on their own, since they do not affect the security of the built image. |

Konflux verifies every pull request against these branches, and builds every push to them without
publishing. Publishing is driven by tags.

### A base branch must be a superset of its post-release branch

A change to a post-release branch must always be applied to the base branch as well, because the
release-time sync discards whatever is on the post-release branch. Renovate is configured so the
updates it files for a base branch are a superset of those it files for the paired post-release
branch, and the daily `uv audit` files each security update against every maintained branch,
which guarantees the matching pull request *exists* - but it still has to be *merged* before
the release. Merging a lockfile fix on `post-release-main` and leaving its `main` counterpart open
past the next release will silently reinstate the older lockfile. Renovate re-files it afterwards,
so the window is one release cycle, but it is a real window.

This applies to each pair independently: `main` must be a superset of `post-release-main`, and
`release-1.7.x` of `post-release-1.7.x`. There is no such relationship *between* pairs - `main` and
`release-1.7.x` are free to diverge.

## Releases

Every published artifact is built from a tag. Pushing a tag that starts with a digit is restricted by
a GitHub ruleset to the `MCP Maintainers` team, and a second ruleset makes such tags immutable: once
pushed, a tag cannot be moved or deleted by anyone. Deciding when to push one is the release
sheriff's job, described below.

### A release tag, such as `1.8.0`, pushed to a base branch

 * Release artifacts are generated (wheel, sdist tarball, zipapps)
 * The release is published to GitHub, PyPI, and the MCP Registry
 * Konflux builds the container and releases it - to quay.io with the `:latest` and `:1.8.0` tags for
   a mainline release, to `registry.redhat.io` for a stable one
 * The paired post-release branch is synchronized to the tag

Note that the container is built from the tag on the base branch, not from the post-release branch.
The sync does not itself produce a published build; it stages the branch that subsequent
`.post<N>` releases are cut from.

### A post-release tag, such as `1.8.0.post1`, pushed to a post-release branch

 * Konflux builds the container and releases it with the `:latest` and `:1.8.0.post1` tags. The
   `:1.8.0` tag is unchanged - it doesn't float.
 * Nothing else. These tags are excluded from the release workflow: there is no PyPI, GitHub or MCP
   Registry release, because the Python sources are those of `1.8.0`, which is already published.

This keeps released containers free of known CVEs without requiring a new semantic version on PyPI.
Mainline containers are not recommended for production, but we still do not want to ship containers
with known vulnerabilities in them.

### The sync

Because a post-release branch may have received lockfile updates since the last release, the sync
cannot be a fast-forward. The workflow performs a specialized merge so that the post-release tree
matches the base branch *exactly*, discarding any drift: an ordinary merge commit - post-release
branch first parent, the release tag second - whose tree is precisely the tree of the release tag
rather than a content merge of the two sides.

Pushing a new `release-1.7.x` branch also runs the sync, to create `post-release-1.7.x` at the tip of
the new branch. Later pushes to `release-1.7.x` do nothing; from then on only a release tag advances
the post-release branch.

## Regressions

There is no specialized rollback procedure.
If a release is buggy, we make a new release to fix it.
If a lockfile update on a post-release branch causes a regression,
then we push a new PR to the post-release branch to fix it,
or make a new release if `pyproject.toml` or code changes are needed.

## Release Sheriff activities

A few activities in this process are deliberately human decisions rather than automation.
A rotating member of the development team, the "release sheriff", carries them out.

Note that the sheriff decides *whether* to release, not just when:
a post-release branch may well accumulate a week of commits that do not justify a container build.

### Monday, for `main`

 * Merge all outstanding maintenance PR's for `main`
 * If there are substantive changes since the previous release:
   * Determine the next version by semver rules
   * Create a release tag and push it to the repository
   * Close all maintenance PR's targeting `post-release-main` (the sync has discarded what they were based on; Renovate will re-file anything still needed)
 * Otherwise:
   * Merge all outstanding maintenance PR's for `post-release-main`
   * If any of these changed what ends up in the container, create a release tag, e.g., `1.8.1.post1`, on the `post-release-main` branch and push it

### Monday, for each `release-1.7.x` branch

 * Merge all outstanding maintenance PR's for `release-1.7.x`
 * If there are Python code changes since the previous release:
   * Create a release tag `1.7.2` and push it to the repository
   * Close all maintenance PR's targeting `post-release-1.7.x`
 * Otherwise:
   * Merge all outstanding maintenance PR's for `post-release-1.7.x`
   * If any of these affected `uv.lock`, `rpms.lock.yaml` or `Containerfile`, create a release tag, e.g., `1.7.1.post1`, on the `post-release-1.7.x` branch and push it
 * If a release was created because of Python changes or `uv.lock` changes, create an updated RPM package (not covered here)

### Asynchronously, when a security vulnerability is reported in a dependency

 * Merge all the PR's (typically duplicated across all `release` and `post-release` branches)
 * Tag a post-release release on all `post-release` branches

## Procedure for creating a new stable branch

 * Create a MR for `konflux-release-data` that:
   * adds a `ProjectDevelopmentStream` CR for `1-7` (which creates a `linux-mcp-server-1-7`  component and application)
   * adds a `linux-mcp-server-1-7` ReleasePlanAddmission CR with `latest`, `1.7` and `{{ labels.version }}`
     in  `.repositories[].tags`.
   * removes `latest` from the previous `linux-mcp-server-1-5` ReleasePlanAdmission CR

 * Determine the branch point on `main`, and create a local branch `release-1.7.x` from it
 * On that branch, point `.tekton/pull_request.yaml` and `.tekton/push.yaml` at the stream's own
   Konflux application and component:

        labels:
            appstudio.openshift.io/application: linux-mcp-server-1-7
            appstudio.openshift.io/component: linux-mcp-server-1-7

   That is the only `.tekton` edit needed. The `on-cel-expression` annotations already match
   `release-*` and `post-release-*`, and Pipelines-as-Code resolves `.tekton/` from the pushed
   ref's own tree - which is also what routes a `1.7.2` tag to `linux-mcp-server-1-7` rather than
   to the mainline application.
 * Push the branch to the repository (must be a member of "MCP Maintainers" team).
   This creates the paired `post-release-1.7.x` branch at the tip of the new branch.
   (Only this first push does so; later pushes to `release-1.7.x` leave the post-release branch
   alone, since from then on only a release tag advances it.)
 * Once the `konflux-release-data` PR is merged, push a `.post<N>` tag on `post-release-1.7.x`
   (e.g. `1.7.1.post1`, based on the most recent release tag reachable from the branch point)
   to trigger an initial release to `registry.redhat.io`

## Procedure for EOL of a stable branch

 * Create a MR for `konflux-release-data` that:
   * removes the `ProjectDevelopmentStream` CR for `1-7`
   * Removes the `linux-mcp-server-1-7` ReleasePlanAddmission CR
     (this is also what freezes the `:1.7` tag - nothing can be released to the stream afterwards)

Removing the CRs is what actually retires the stream: MintMaker stops scanning the branches, and
nothing can be released to the registry any more.

Renaming the branches out of the way is cosmetic on top of that - it takes them out of the CI and
Konflux branch filters, which all match `release-*` and `post-release-*` by prefix. It is also
**not currently possible**: renaming a branch deletes the old ref, and the *Restrict branch
deletion (release)* ruleset has no bypass actors, deliberately - being able to delete and recreate
a `release-*` branch would be a way to put unreviewed content into a stream that already has a
working ReleasePlanAdmission behind it.

So before the first EOL, decide one of:

 * leave the branches in place, retired by the CR removal alone, and accept that they keep
   receiving Renovate and CI activity;
 * have a repository admin disable the deletion ruleset for the duration of the rename;
 * add a workflow that performs the rename, with the release App allowlisted for deletion - which
   reintroduces the delete-and-recreate path unless the workflow constrains it.

There is a year before this matters.

## RPM Builds

RPM builds are done manually. This is done on each release from a stable branch, but also if there are any changes merged to `uv.lock` on the corresponding post-release branch.
The way this works is that the separate dist-git repository has an `update.sh` script: the engineer runs `update.sh <commit>`, passing the tag to update to.
This creates the sdist and dependency tarballs with the appropriate version, updates the spec file, and files a merge request to RHEL GitLab.

## Versioning

Base tagged versions are semver versions.

*   `1.8.0` - a release with new features.
*   `1.8.1` - a release with only bug fixes.
*   `2.0.0` - a version that is significantly incompatible with previous releases, or a major rewrite.

A `.post<N>` suffix indicates a version whose Python sources are identical to a base version,
but which was built with updated lock files or a newer base image.
`<N>` simply counts up from 1 within a base version; it is chosen by the release sheriff
when creating the tag, not computed from the repository history.
These versions are never released to PyPI.

Every published artifact is built from a tag, so its version is just the tag:
there is no separate version-computation step, and setuptools-scm reports the tag verbatim.
This does require the Konflux clone to be deep enough to see the tag.

hatch-vcs is set up to use the `guess-next-dev` scheme, so for untagged commits -
after the 1.8.0 release, say -
the autogenerated version is similar to `1.8.1.dev2+g12314121`,
regardless of whether the next release turns out to be 1.8.1 or 1.9.0.

These generated versions appear only in verification builds.
They are not released to a public container registry,
and importantly, are not released as RPMs,
since RPM does not understand the Python `.dev` release setup
(`rpmdev-vercmp` reports `1.8.1.dev1 > 1.8.1`, which is the wrong way round).


## Security and Branch Protection

`release-*` branches get the same branch protections as `main`.

The `post-release-*` branches are protected by a stricter ruleset of their own: **nobody can push to
them**, not even the `MCP Maintainers` team. Maintainers have expanded powers elsewhere - creating
release branches, pushing release tags - but not the power to put arbitrary content in front of
users, which is what a direct push to a post-release branch would be.

The only thing that can write to them is a custom GitHub App acting as a service account,
allowlisted in that ruleset. It exists because the sync has to record a very specific merge commit
without opening a pull request, which no pull-request-based flow can do.

That makes the App's credentials more powerful than any human, so what may use them matters:

 * The App's secrets live in a GitHub Environment restricted to the `main` branch.
 * The sync runs on `workflow_run`, which always executes the copy of a workflow on the default
   branch. Pushing a tag or a `release-*` branch runs a separate trigger workflow that holds no
   credentials and does nothing but fire.

The indirection is the point. A workflow triggered directly by `on: push` runs the copy of itself
found in the *pushed ref's* tree, so a maintainer could push a tag carrying a modified workflow and
be handed the App token with no review. Splitting the pair means the half that holds the credential
is always reviewed code on `main`.

## Justification for the Special `post-release` Branch Handling

In what follows, the "base branch" is `main` or a `release-1.7.x` stable branch, and the post-release branch is the `post-release-*` branch paired with it.

*   We need a branch whose content is the released source plus only lockfile / base image updates, for Renovate/MintMaker and Konflux to work from - hence we can't just build from the base branch.
*   We want one post-release branch per base branch, not one per release. A `post-release-x.y.z` branch for every release would accumulate 20-30 a year, and neither Konflux nor Renovate can be configured to act on "the most recent `post-release-*` branch" without editing their configuration at every release. Since there are at most three base branches at a time, a fixed-name post-release branch for each is tractable; a branch per release is not. Hence each release has to be merged into the existing post-release branch, or overwrite it.
*   Every Konflux build corresponds to a specific git commit. We want these commits to be in the repository, not just dangling and potentially garbage collected. Hence we need merge commits instead of overwriting.
*   The merge deliberately discards the post-release side: the resulting tree is exactly the base branch's tree, not a content merge of the two. This is what guarantees that what we ship is what is on the base branch, and that no change can reach users without going through the base branch first. (Since stable branches take only backports, in practice that also means nothing reaches users that was not on `main` first.)
*   Git has no merge strategy that does this - `-X theirs` resolves *conflicting hunks* in favour of the other side but keeps post-release-only changes that do not conflict, which is not the same guarantee, and on `uv.lock` can splice two independently resolved lockfiles into one that matches neither. So the workflow forces the tree explicitly:

        git merge --no-commit --no-ff "$tag" -s ours
        git read-tree -m -u "$tag"
        git commit

    Parent order is the conventional one (`post-release-main` first). Nothing depends on it any more; an earlier draft reversed it so that `git describe --first-parent` would find the release tag, which is unnecessary now that every published build is made from a tag of its own.
